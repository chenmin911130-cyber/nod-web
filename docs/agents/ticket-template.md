# 执行单模板

每一张交给实现代理的 GitHub issue（执行单）都必须包含下面 §0–§6 全部小节，缺一节就不算执行单。写单的人对照文末「写单自检」过一遍再发；审查的人按 §5 逐条核 PR，没跑到的项不放行。

用 `gh issue create --title "执行单 · <一句话>" --body-file <file>` 创建，正文用下面的结构。

---

## 0. 交付与边界

固定写法，按实际填空：

> 交 <Grok | Composer>（二者规则相同，见 `AGENTS.md` 分工）。从执行时最新 `origin/main` 开隔离 worktree `.worktrees/<issue-id>/`，不要用当前脏工作区。独立 PR，不合并、不部署、不装机、不 `cap:sync`、不 bump bundle。不与 #<其他单> 混进同一个 PR。

## 1. 触发条件与期望行为

- **触发条件**：用户做了什么 / 系统处于什么状态时出现问题。写成可复现的步骤或可观察的状态，不写「有时候」。
- **期望行为**：修好之后应该看到什么。写成可以被 §5 的命令或真机步骤验证的陈述。
- **现状**：现在实际看到什么（错误文案、HTTP 码、日志行、截图路径）。

## 2. 根因证据

- **基线**：`origin/main` 的 40 位 SHA，加短 SHA。所有行号以这个基线为准。
- **证据**：`文件:行` + 一句话说明这段代码为什么导致 §1 的现状。能贴的贴原文（`sips` 输出、日志、payload、测试失败栈）。
- **未确认的部分逐条标 `[未确认]`**：例如「静态审查结论，尚无线上复现」「Apple 审核通常不认，非条文明确」。不要把推断写成事实。
- 与已合并 PR 的关系：哪些地方已经修过、不要重复修（给 PR 号）。

## 3. 修改范围 / 禁止顺手改

- **改什么**：按文件列，写到函数 / 键名级别。
- **不改什么**：明确列出执行者可能顺手动但本单不许动的东西——全局配置（如 `autoflush`）、其他登录路径、事件映射、套餐、Web 端、Android、版本号、`cap:sync` 产物、无关文案。
- 需要用户在仓库外做的事（Apple Developer 勾 capability、Railway 变量）单独一条，写明是用户做，执行者在 PR 描述里提醒。

## 4. 回归测试与边界条件

- 新增测试的文件名和每条测试要断言什么。断言必须落在**持久化结果 / 产物 / 真实接口响应**上，不能只看返回 JSON 或同一个已 detach 的 ORM 对象。
- 参照哪个现有测试的风格（给路径）。
- **边界条件**逐条列：空值、第二次调用、并发、过期、已删除、naive/aware 时间、第三方只在首次返回的字段、不同数据库语义（SQLite vs Postgres）等。
- 失败注入要写清**在哪一层注入**（例如「`Session.flush` 抛错」而不是「让密码哈希失败」），注入点必须在被测的持久化路径上。
- 修复前要能跑出失败、修复后通过。PR 里要贴两次的命令与结果。

## 5. 验收命令与通过标准

只写**仓库里真实存在**的命令。开单前用 `rg -n "<脚本名>" package.json web/package.json` 确认。当前可用的标准命令：

| 范围 | 命令 |
|---|---|
| 服务端 | `pytest tests/<新文件>.py tests/<相关现有文件>.py`（`pytest.ini` 已设 `pythonpath = .`） |
| Web 单测 | `npm --prefix web test`（全量）或 `npx tsx web/src/<file>.test.ts`（单文件） |
| Web e2e | `npm --prefix web run test:e2e -- <spec>`（仅在单里点名时跑） |
| 原生编译 | `npm run check:ios`（改了 `ios/**/*.swift`、`plugins/nod-*/ios/**`、Podfile、pbxproj 时必跑） |
| 交付脚本 | `npm run test:ios-deliver`、`npm run test:ios-compile-gate`（改了 `scripts/ios*` 时） |
| 产物检查 | `sips -g hasAlpha <png>`、`plutil -lint <plist>`、`plutil -p <bundle>/Info.plist` 等，写出期望输出 |

**没有 `npm run test:golden` 这个脚本**，不要写。**GitHub Actions 已关闭（付费额度，2026-09 起）**，`gh run list` 不会有新结果，不能作为任何证据；PR 里贴的本地命令输出是唯一的测试证据，缺了就等于没跑。

PR 描述必须包含两段原样输出（可截断到失败断言行 + summary 行）：

1. **修复前失败**：在 `origin/main` 基线上只加新测试、不加修复，跑 §5 的测试命令，贴失败输出。证明测试真的咬得住原问题。
2. **修复后通过**：加上修复后再跑同一条命令，贴通过输出，含用例数。

只有第 2 段、没有第 1 段的 PR 按「回归覆盖未证明」处理。

每条验收写成「命令 → 期望输出」：

- `pytest tests/test_x.py` → 全绿，并列出 N 条用例名。
- `git diff --stat origin/main` → 只含 §3 列出的文件。
- 真机 / 人工验收单列，注明「用户做」，写具体操作和期望画面。

**通过标准**一句话，指向可观察结果，不指向「接口返回 200」：例如「用全新 `db_session` 读库，新密码 `verify_password` 为真、旧密码为假、`used_at` 非空」。

## 6. 执行者质疑条款

固定写法，原文放进每张单：

> 执行前先按 §2 的 `文件:行` 核一遍根因。证据对不上（行号不对、代码已变、复现不出来、修法会破坏 §3 的禁改项），**先在本 issue 评论反馈，不要硬按单改**。有更简单或更安全的修法也先评论，等回复再动手。发现单外的同类问题，评论里记一笔，不并进本 PR。

---

## 写单自检

- [ ] §0 写了交谁、worktree 路径、不与哪张单混 PR
- [ ] §1 触发条件可复现，期望行为可被 §5 验证
- [ ] §2 有基线 SHA，每条证据有 `文件:行`，未确认项都标了 `[未确认]`
- [ ] §3 「不改什么」至少列出 3 项执行者最可能顺手动的东西
- [ ] §4 每条测试写了断言落点，边界条件逐条列，失败注入点在持久化路径上
- [ ] §5 每条命令在仓库里确认存在，每条有期望输出，通过标准不是「返回 200」
- [ ] §6 质疑条款原文在

## 验收结论定义

审查结论只有三档，写在 PR 评论第一行，不再单写「PASS」：

| 结论 | 含义 |
|---|---|
| **不放行** | 下面任一条不满足且实现方未补齐 |
| **静态审查通过** | diff 对得上 §3，无越界、无未处理高风险；但 PR 缺测试证据（没有修复前失败 / 修复后通过输出，或缺 §5 某条命令的记录）。**只看了 diff 没看到测试跑过，就只能写这一档。** |
| **验收通过** | 下面四条全部满足 |

验收通过的四条：

1. **回归覆盖原问题**：PR 里有「修复前失败 / 修复后通过」两段输出，失败的断言正是 §1 描述的问题。
2. **相关模块测试与必要检查通过**：§5 每条命令在 PR 里有原样输出，用例数与新增测试对得上；动过 Swift / Podfile / pbxproj 的有 `npm run check:ios` 输出。
3. **无超范围修改、无未处理高风险**：`git diff --stat origin/main` 只含 §3 的文件；审查提出的高风险点都已改或已在 issue 里明确接受。
4. **并行任务合并后有集成验证**：同一批（同一天 / 互相碰文件）合入的多张单，最后一张合并后在 merged `origin/main` 的干净 worktree 上跑一遍：`pytest -q`、`npm --prefix web test`，动过原生的加 `npm run check:ios`；输出贴到该批最后一张 issue 的评论里，再关整批 issue。CI 关闭期间这一步由 Fable 跑——这是 Fable「审查不跑本地测试」规则唯一的例外，只跑上面这套固定命令，不搭复现、不改代码。

## 审查规则（Fable / 验收方）

- 按 §5 逐条对 PR：每条命令 PR 里要有对应记录和结果。**单里要求的没跑、或跑的不是单里那条，PR 不放行**，让实现方补齐再合；没有「不阻塞的备注」这一档。
- 没看到「修复前失败」输出，最高只能给「静态审查通过」，并在评论里写明缺什么。
- §4 要求的失败注入点与 PR 实际注入点不一致，视为未测。
- §3 禁改项出现在 diff 里，视为越界，即使改得对。
- 执行者按 §6 提出质疑时，先回应质疑，再决定改单还是改 PR；不要跳过。
- 审查本身不跑本地测试、不搭复现（见 `AGENTS.md` 分工）；看 diff、PR 里的测试记录、以及要不要 `cap:sync` / bump。
